## 三、检索与记忆类

|---|---|---|---|---|---|
| **RAG**（检索增强生成） | 先从知识库检索相关片段、再拼入上下文让 LLM 作答，减少幻觉 | 无协议，工程范式；各框架/云原生支持 | 本项目知识底座：course 方法论、过往项目复盘、渲染参数经验入知识库，供各操作员节点检索 | **全力采用** | https://hanbz.dev/articles/context-engineering-enterprise-ai-agent-guide-2026 |
| **Embedding / 向量数据库** | 把文本映射为向量做语义相似检索；向量库（Qdrant/FAISS/pgvector 等）是其存储引擎 | 成熟工程组件 | 已实测 **text-embedding-v4**（百炼）；知识库检索用"结构化元数据过滤 + 向量排序"两段式 | **全力采用**（已实测） | https://blog.csdn.net/LDZKKJ/article/details/162525894 |
| **Agentic RAG** | 让 Agent 自主决定何时检索、检索什么、多轮迭代检索-验证，而非固定"一次检索"管线 | 工程范式，LangGraph/LlamaIndex 等框架原生支持 | 复杂节点（如"剧本顾问""考据员"）用 Agentic RAG 多轮检索；简单节点用固定 RAG 即可，避免过度工程 | **P1 试点**（仅在高检索需求节点） | https://www.digitalapplied.com/blog/agent-memory-architectures-vector-graph-episodic |
| **GraphRAG / 知识图谱记忆** | 在向量检索之上加实体关系图遍历，支持多跳推理与时序事实（如 Zep/Graphiti 双时态图） | Zep Graphiti、Neo4j、Mem0 graph layer 等；生产共识是"向量+图"混合，仅实体推理密集时才上 | 影视知识多为流程/经验型，实体关系推理需求弱；角色关系等场景可后置 | **观察**（防止过度工程化） | https://agentmarketcap.ai/blog/2026/04/08/agent-long-term-memory-architecture-letta-memgpt-langmem-zep https://agentmarketcap.ai/blog/2026/04/06/distyl-ai-175m-enterprise-knowledge-graphs-agent-memory-layer |
| **长期记忆系统（Mem0 / Letta / Zep / LangMem）** | 跨会话持久化 Agent 记忆的独立技术层：Mem0（托管、向量+图+KV 三层）、Letta/MemGPT（OS 式 Core/Archival/Recall 三层，Agent 自管分页）、Zep（双时态知识图）、LangMem（语义/情景/程序三分法） | 独立产品/开源框架；2026 上半年成为独立赛道（mem0 融资 $24M，各框架均出 memory API；Anthropic 也出了官方 memory tool） | 本项目操作员节点大多是单会话任务；跨会话需要的是"项目级白模/决策记录"（文件系统即可）而非对话记忆。可先按 Letta 三层思路分层管理项目状态文件 | **观察**（先用文件型项目记忆，对话记忆后置） | https://agentmarketcap.ai/blog/2026/04/08/agent-long-term-memory-architecture-letta-memgpt-langmem-zep https://superkind.ai/blog/ai-agent-memory |
| **Context Engineering（上下文工程）** | 系统性治理模型每一步"看见什么"：指令、工具定义、检索证据、历史、实时状态的选取/压缩/排序/预算分配，是 2026 年取代 prompt engineering 的生产纪律 | 无协议，工程范式（Anthropic/Manus/Google Cloud Next 2026 推热）；研究表明 60–80% Agent 失败源于上下文而非模型 | **本项目第二支柱的隐形地基**：每个操作员节点的系统提示 + 交接包注入内容 + 工具 schema 都是上下文工程对象；交接包要"精确够用"，防止塞满导致 context rot | **全力采用**（写进各节点设计规范） | https://www.omnidatatec.com/insights/prompt-engineering-is-becoming-context-engineering https://subagentic.ai/posts/context-engineering-missing-layer-agentic-ai/ https://designedbyai.io/knowledge/what_are_the_context_engineering_best_practices_for_production_ai_systems_in_2026.php |
| **Context Rot（上下文腐烂）** | 上下文越长/越乱，模型检索正确信息的能力越差的实证现象（Chroma 实验：同样文档不同组织方式，准确率 98%→64%） | 学术/工程实证，非协议 | 印证"交接包分层、只传必要白模数据"的设计；长任务节点要做上下文折叠/压缩 | **全力采用**（作为设计原则） | https://blog.csdn.net/LDZKKJ/article/details/162525894 |

## 九、本项目结合建议（"LLM + 名词"优先级清单）

### P0 立刻用（骨架层，已在用或成本极低）

| 组合 | 理由 |
|---|---|
| **LLM + Function Calling + Structured Output** | 一切操作员节点的动作基础，llm_gateway 已跑通；所有交接包/评分卡强制 schema 校验 |
| **LLM + MCP** | 工具交付统一底座，r17-8a 已试点双组件；新工具一律 MCP Server 化，杜绝散装脚本直调 |
| **LLM + RAG + Embedding（text-embedding-v4）** | 已实测；course 方法论/项目复盘/渲染经验入知识库，"结构化过滤+向量排序"两段式检索 |
| **LLM + Agent Skills（SKILL.md）** | 把 15 岗方法论与渲染流程封装为技能包；与 MCP 分工明确——MCP 给手、Skills 给判断 |
| **LLM + Context Engineering** | 零成本高杠杆：交接包"精确够用"、防 context rot、上下文分层（指令/检索/状态分预算）写进节点设计规范 |
| **LLM + AGENTS.md** | 仓库根加一份，所有开发/操作 Agent 自动对齐项目规范，半天工作量 |
| **LLM + Guardrails + HITL** | 抽卡选片、预算超限、参数越界三处必须人工闸门 + schema 拦截，直接复用既有决策记录 |

### P1 试点（杠杆明确但需验证，避免一刀切铺开）

| 组合 | 理由 |
|---|---|
| **交接包对齐 A2A 数据模型** | 不上完整协议栈，只对齐 task/artifact 结构与 Agent Card 式节点能力描述；未来跨管道协作零迁移 |
| **LLM-as-Judge 抽卡评分** | 额度大头在抽卡；先小样本校准 judge 与主理人偏好一致性（一致率达标再放开），人工只复决 Top-N |
| **小模型路由** | 额度耗尽现实下最划算：80% 简单任务（校对/打标/格式转换）走小模型，路由收口 gateway；先从字幕校对试点 |
| **Trace + per-task 成本观测** | 自研轻量落日志，字段对齐 OTel GenAI（session/trace/span），月度复盘直接用；平台化（Langfuse 类）等量起来再说 |
| **AG-UI 简版（状态流式）** | 操作员面板先做 SSE 进度推送，让主理人看见每个节点在干什么；完整 Agentic UI 后置 |
| **Durable Execution 检查点** | 全帧数渲染小时级，节点边界落盘批次状态，失败续跑不做重复功；自研简版即可 |
| **Code Interpreter（数据任务）** | 剪辑/统计节点处理 EDL、镜头表、渲染报表时引入，配目录级沙箱 |

### 观察与克制（防止过度工程化）

| 组合 | 不急的理由 |
|---|---|
| **GraphRAG / 知识图谱记忆** | 影视知识以流程/经验为主，实体多跳推理需求弱；等角色关系类检索成为真实痛点再上 |
| **对话式长期记忆（Mem0/Letta 类）** | 操作员多为单会话任务；项目状态用文件型分层记忆（Core/Archival 思路）已够 |
| **完整编排框架（LangGraph/CrewAI 等）** | 自研轻量编排 + gateway 已成型；迁移有成本。触发条件：编排逻辑复杂到自研开始出 bug 时优先评估 LangGraph |
| **Computer Use / Browser Use** | 工具链全程 API/MCP，仅作无 API 国产软件的兜底方案备案 |
| **去中心化协议（ANP/DID/链上身份）与支付协议（AP2/UCP/x402）** | 单团队内部管线无跨组织信任与支付场景；跟踪 ANP 一条线即可 |
| **Swarm / 涌现式多 Agent** | 影视管线是确定性流程，涌现不可控；并行抽卡用普通并发调度足够 |
| **WebMCP / MCP Apps** | 浏览器协议在 Chrome Canary 预览期、MCP Apps 生态早期；等稳定 |

**一句话总结**：P0 六件套（Function Calling / MCP / RAG / Skills / 上下文工程 / Guardrails+HITL）构成骨架；P1 六项（A2A 式交接包、LLM-as-Judge、小模型路由、Trace、AG-UI 简版、检查点）按节点逐个验证；其余全部"观察、不铺开"——技术上多元跟进，落地上分档克制。
