# 自包含 Blender 控制层方案调研（R17-8 老板裁定）

> 日期：2026-10-04
> 调研人：r17-8-blender-mcp
> 输入：老板裁定——"用 MCP 但是又让项目自包含"：既享受 MCP 式交互控制能力，又不依赖外部第三方服务/插件。
> 现状基线：`AI影视团队v2/tools/blockout_batch_render.py`（subprocess 调 Blender 5.2.2 headless，批量渲染白模），无 MCP 层。

---

## 0. 结论速览（TL;DR）

**老板的折中方案成立，且有大量先例支撑。** 推荐架构：

- **主线（推荐）：自研双组件"MCP 兼容层"（路线 C+D 融合）**——项目自带的 Blender addon 内嵌 socket/JSON-RPC 服务端（在 Blender 进程内执行 bpy），项目自带一个轻量 stdio MCP server（只做协议翻译，对自家 agent 暴露）。两个组件全部随项目分发，运行时零外部第三方依赖。
- **备选：保留纯 bpy subprocess（路线 B）作为批量渲染主干**。MCP 交互层是增量叠加而非替换；若 MCP 层故障，批量渲染随时可回退 B。

**关键 License 事实**：MCP 协议是开放标准（MIT，2025-12 起归 Linux Foundation 旗下 Agentic AI Foundation）；blender-mcp 类项目 MIT 可自由借鉴；Blender addon 因 import bpy 须以 GPL 兼容许可分发——但这不阻碍商业化，因为核心 IP（管线、提示词、控制图、云端编排）可留在 GPL 边界之外的独立进程中。

---

## 1. 四条路线对比

### A. 外部 blender-mcp（第三方现成品）

**原理**：双组件架构——(1) Blender addon 在 Blender 内部启动 TCP socket 服务器（默认 9876），接收 JSON 命令并调用 bpy 执行；(2) 独立的 MCP server 进程实现 Model Context Protocol，通过 stdio 与 LLM 客户端（Claude/Cursor）通信，通过 TCP 转发给 addon。

**代表项目**：[ahujasid/blender-mcp](https://github.com/ahujasid/blender-mcp)（已更名 mcp-for-blender，PyPI 包 `mcp-for-blender`）。

**事实核查**（截至 2026-09）：
- License：**MIT**——允许商用闭源捆绑分发（来源：[claudeers.com/blender-mcp](https://claudeers.com/blender-mcp)、[robotworld.top](https://robotworld.top/en/tags/DCC%20Integration)）。
- 活跃度：约 26.9k–29.2k stars / 2.5k forks，README 自述"actively maintained"（last commit 近期），社区规模大（来源：[tmtpost](https://www.tmtpost.com/agent/ai-article/20232)、[claudeers](https://claudeers.com/blender-mcp)）。
- 但**不是官方**：Blender 官方组织无任何 MCP 项目，README 明确声明 "This is a third-party integration and not made by Blender"（来源：[dcc-mcp-blender 对比文档](https://github.com/loonghao/dcc-mcp-blender/blob/main/docs/blender-mcp-comparison.md)）。

**优点**：开箱即用、工具面完整（32 个工具，含 execute_code 逃生舱）、生态大。
**缺点/风险**：
- addon socket **无认证无加密**，能连上端口即可在 Blender 里执行任意 Python（来源：[dcc-mcp-blender 对比](https://github.com/loonghao/dcc-mcp-blender/blob/main/docs/blender-mcp-comparison.md)）——商业化交付给客户时有安全隐患；
- 单人维护（ahujasid），长期可用性存疑（同上来源）；
- 运行时依赖 PyPI/uvx 拉包——**不满足"自包含"**；
- 工具集面向通用建模探索，与本项目"白模批量渲染→控制图"管线不贴合。

### B. 纯 bpy subprocess 自研（现状）

**原理**：编排脚本（项目自有 Python）以 `blender --background --python xxx.py` 子进程方式调 Blender，脚本内用 bpy 建场/渲染后退出。

**事实核查**：
- 官方确认 Blender 可任意商用，产出物（.blend/渲染帧）完全归用户所有（来源：[blender.org/about/license](https://www.blender.org/about/license/)、[blender.org/faq](https://www.blender.org/faq/)）。
- License 边界：若**对外分发**调 bpy 的 Python 脚本，须以 GPL 兼容许可开源（官方 FAQ："If you share or publish Python scripts they have to be made available licensed as GNU GPL as well"）；仅内部/服务端使用（SaaS）则无分发即无义务（同上来源）。
- **进程隔离豁免**：FSF 界定 socket/文件交换为"arm's length"——核心逻辑放在 Blender 进程外的独立程序中可保持闭源，进程内的小桥接脚本才需 GPL（来源：[cookstation.blog GPL 合规指南](https://www.cookstation.blog/blender-scripts-gpl-compliance-guide)，标注：此为行业通行解读而非官方裁决，未验证于法院判例）。

**优点**：零运行时外部依赖；已建成并投产（#32/#36 已完成）；无常驻进程、无端口暴露，最适合无人值守批量渲染。
**缺点**：每次调用冷启动 Blender（秒级）；无交互式"所见即所得"控制；无 MCP 式工具发现——大模型无法实时探查场景状态、迭代调整；与老板"用 MCP"的诉求不符（单独作为唯一层时）。

### C. 自研内嵌 socket/JSON-RPC addon

**原理**：把 blender-mcp 的核心机制（Blender 内 socket 服务端 + JSON 命令执行）**自己实现并随项目分发**，不装第三方插件。MCP server 部分可以省略（自家 agent 直连 socket）或配一层薄协议翻译。

**技术可行性与先例（充分验证）**：
- [minihellboy/claude-blender](https://github.com/minihellboy/claude-blender)：addon 内实现完整 **JSON-RPC 2.0** 协议处理器（`protocol.py`），`blender --background --python headless_blender.py -- --port 9876` 证明 **headless 模式下 socket 服务端照常工作**（仅视口截图/undo 不可用）——与本项目现状管线完全兼容。
- 关键工程要点（来源：[abdelouafitahiri/claude-blender 技术说明](http://ghub.com/abdelouafitahiri/claude-blender)）：**bpy 非线程安全，不能用 threading.Thread，须用 `bpy.app.timers` 在主线程轮询执行命令**，否则崩溃。这是自研时必须复刻的核心知识。
- 协议形态自由：可为纯 JSON over TCP（ahujasid 的简化格式 `{type, params}`），也可为标准 JSON-RPC 2.0（后者可平滑升级到 MCP 兼容）。

**优点**：完全自包含；协议/工具集按自家管线定制（camera 轨、白模、控制图导出）；无第三方供应链风险；socket 服务端可自加 token 认证与仅监听 127.0.0.1。
**缺点/风险**：需自行开发与维护（但核心约几百行，有大量参考实现）；addon 若对外分发须 GPL（同路线 B 的 License 边界，见下文"GPL 边界与商业化"）。

### D. MCP 兼容自托管（内嵌 stdio MCP server）

**原理**：项目内嵌一个 stdio MCP server 进程，只对自家 agent 暴露。它不连第三方服务，只是把"自家工具"翻译成 MCP 协议，让任何 MCP 兼容客户端（含未来客户侧 agent）都能调用。

**事实核查（协议开放性）**：
- MCP 由 Anthropic 于 2024-11-25 开源发布，规范与参考实现 **MIT**（新贡献 Apache-2.0 / CC BY 4.0）（来源：[aiwiki.ai](https://aiwiki.ai/wiki/model-context-protocol)、[genai.club](https://genai.club/blog/what-is-mcp-model-context-protocol)）。
- **2025-12-09 起捐赠给 Linux Foundation 旗下 Agentic AI Foundation（AAIF）**，厂商中立治理，OpenAI/Google/Microsoft 均已采纳——协议被单一公司控制的顾虑已消除（来源：[agenticcommerceprotocol.info](https://agenticcommerceprotocol.info/standards/mcp)、[aiwiki.ai](https://aiwiki.ai/wiki/model-context-protocol)）。
- 自托管完全可行：官方 Python/TS SDK MIT，最小 server 约 40 行；当前稳定规范版本 2026-07-28（来源：[genai.club](https://genai.club/blog/what-is-mcp-model-context-protocol)、[aiwiki.ai](https://aiwiki.ai/wiki/model-context-protocol)）。

**优点**：得到 MCP 生态兼容性（Claude Desktop/Code、Cursor 等客户端即插即用）而不引入任何运行时外部依赖；SDK 可 vendor 进项目或仅作构建期依赖；商业化时"客户自带 agent 即可驱动"是卖点。
**缺点**：多一层进程与协议维护；SDK 依赖需锁定版本（低风险，MIT + 基金会治理）。

## 2. 商业化依赖风险矩阵

| 路线 | 外部依赖程度 | License 风险 | 分发复杂度 | 开发成本 |
|------|:---:|:---:|:---:|:---:|
| **A 外部 blender-mcp** | **高**（PyPI/uvx 运行时拉包 + 单人维护项目） | 低（MIT） | 中（客户需装 addon+uv） | 低（开箱即用） |
| **B bpy subprocess（现状）** | 低 | 中（脚本对外分发须 GPL；SaaS 内用无义务） | 低 | 低（已建成） |
| **C 自研内嵌 socket addon** | 低 | 中（addon 须 GPL，核心 IP 可留进程外） | 中（addon 打包随项目分发） | 中（数百行，参考实现充分） |
| **D MCP 自托管** | 低（协议开放+MIT SDK，可 vendor） | 低 | 中（多一层进程） | 中 |

> GPL 备注：对本项目而言，无论 B/C，凡随项目分发的 bpy 相关 Python 脚本都应以 GPL 兼容许可提供（如 GPL-2.0+）。这不构成商业障碍：官方 FAQ 明确允许收费分发（只限制买方转售限制权），且本项目核心价值（master_v2.json 时间线、提示词库、控制图资产、云端 VACE 编排、llm_gateway）均不 import bpy，可保持专有。

## 3. 推荐架构："MCP 兼容、自研自包含"双组件层

```
自家 Agent（MCP 客户端）
   │  stdio (MCP 协议, JSON-RPC 2.0)
   ▼
[组件2] 自研轻量 MCP server（随项目分发，Python，~百行）
   │  TCP socket 127.0.0.1:9876（JSON-RPC，带 token 校验）
   ▼
[组件1] 自研 Blender addon 内嵌 socket 服务端（随项目分发，GPL-2.0+）
   │  bpy.app.timers 主线程轮询执行
   ▼
Blender 5.2.2（Steam 版 / headless 均可）
   ├─ 交互模式：老板带 UI 的 Blender 实时建模/摆机位，agent 通过 MCP 实时探查+修改
   └─ 批量模式：blender --background --python addon_boot.py（先例：minihellboy/claude-blender 已验证 headless 可行）
```

**为什么这个折中成立**：
1. "用 MCP"——agent 侧是标准 MCP 协议，协议本身是 Linux Foundation 托管的开放标准（MIT），不是对任何第三方服务的依赖；
2. "自包含"——两个组件都是自家代码随项目分发，运行时不调 PyPI/uvx、不装第三方插件；官方 SDK（MIT）可 vendor 或仅作开发期依赖，钉版本即可；
3. 与现状兼容——批量渲染主干（B）继续用，MCP 层按需叠加：C 与 B 可共用同一批 bpy 场景构建函数（抽成共享模块），两套入口、一套核心；
4. 商业化安全——addon 遵 GPL 开源不影响壁垒（核心 IP 在进程外），且比第三方无认证 socket 更安全（自加 token + 仅回环监听）。

**何时切换/回退**：
- **主线降级触发器**：若维护双入口成本过高或 MCP 层出现难以定位的稳定性问题 → 回退 B（subprocess 批量渲染不依赖 MCP，已投产，随时可用）。
- **升级触发器**：若未来需要接入更多第三方 agent / 客户生态 → D 层协议已就位，直接暴露即可，无需改造。
- **明确不建议**：A 路线作为商业化交付形态（运行时外部依赖 + 单人维护项目 + 无认证 socket，三条均触雷）；但开发期可用 A 快速做交互实验，其 addon.py（MIT）架构可直接参考借鉴。

## 4. 落地最小步骤（供后续排期参考，本轮不实施）

1. 抽取 `blockout_batch_render.py` 中 bpy 场景构建逻辑为共享模块（addon 与 subprocess 脚本共用）；
2. addon：`bpy.app.timers` 轮询 + JSON-RPC 2.0 handler + `execute_code`/`get_scene_info`/`render_frame` 三个起步工具（参考 minihellboy/claude-blender 与 ahujasid addon.py，均为可借鉴许可）；
3. MCP server：官方 Python SDK 钉版本，stdio transport，三个工具透传；
4. 安全基线：仅监听 127.0.0.1、启动时生成 token、命令白名单 + `execute_code` 可配置关闭；
5. 自测：headless 模式跑通"建场→摆机位→渲 24 帧→出控制图"全链路。
