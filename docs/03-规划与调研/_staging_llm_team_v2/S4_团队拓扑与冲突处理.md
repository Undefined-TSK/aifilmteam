# 任务一 · 团队拓扑：老板七问逐条

## ① 老板（主理人）在团队中是什么角色？

**结论：四重身份合一——最终责任人 + 审批人 + 仲裁者 + 产品负责人，且全部机制化为"三介入门"，不做日常指挥。**

逐项论证（每条挂事实）：

| 身份 | 机制落地 | 事实依据 |
|---|---|---|
| **最终责任人** | AI 不署名、责任人类终担；authorship 仅归人类 | DECISIONS.md:725（PH2："AI＝执行臂+受限协作者；意图归属人类、责任人类终担、AI 不署名"）；对齐美国版权局 human authorship（DECISIONS.md:716） |
| **审批人** | ① intent_graph 导演签收（17d §6.2"signoff=导演保留，人类意图归属"）；② 锚点签收（B2，master_v2 signoff 机制不变，17d §2.6-2）；③ 人审卡片裁决（R17-9-4 先例：DECISIONS.md:858"11:1x 卡片裁决"）；④ 熔断解锁——"熔断后不自动恢复，必须老板签字解锁"（三.md:896） |
| **仲裁者** | "老板终裁→导演管艺术→制片管流程"权力层级；"老板发言=终局"；方向级分歧老板拍板 | 三.md:783-784（5.4 协作协议第 2/3 条） |
| **产品负责人** | 哲学级需求由老板直接裁定（非团队建议）：R17-8 管线哲学修正"1:1 复刻→白模为骨、AI 为肉"（DECISIONS.md:827）；K-REV-1~4 本地优先直接修订四处（DECISIONS.md:760-770）；R17-1 白模双环节=项目核心定位（DECISIONS.md:787） |

**与三介入门的关系**：以上四重身份**只在三处兑现**——三档位指令（locked/proposed/free 标注任务简报）、锚点签收、人审卡片（17d §2.6，R17-8b 原文"老板=导演，只在三档位指令、锚点签收、人审卡片处介入"，DECISIONS.md:834）。三介入门之外老板是**隐形股东**而非操作经理：既有制度明文"全部走推荐，之后不用我拍板"（第九轮起团队收敛规则，DECISIONS.md:418）。

**归类判定**：若必须单选，老板是**最终责任人（accountability 终点）兼任审批人**——仲裁者与产品负责人职能均可委托/降频（仲裁已被"契约即规则"分流，见任务二⑤；产品需求已被 15 轮决策 corpus 固化），唯有"责任人类终担"（PH2）与"熔断签字解锁"（三.md:896）两项不可让渡。

## ② 每个 LLM 是员工/工具/外包商/顾问还是代理？法律与责任身份如何落地？

**结论：编制上是"员工"（有岗位卡、有培养流程、可被打回可晋升），责任上是"受限协作者+可审计执行臂"。**

- **是员工而非工具/外包商/顾问**的依据：①有编制——B17d-5"五操作员编制替代旧五岗"（DECISIONS.md:845；17d §6.3 编制表）；②有身份卡——operator_card.json 每节点一张（17d §5.2）；③有培养流程——"从零培养一个新数字员工"checklist（培养手册 §1.6:128-140，岗位卡落盘→skill 装载→escalation 三条件）；④有记忆与成长——op_log 每日教训行回灌 RAG 经验层（培养手册 §1.5:122-126，Generator-Reflector 闭环）；⑤老板哲学明文"每个 LLM 是有手有脚的真实的人"（17d §0 总纲；R17-8b DECISIONS.md:834）。
- **不是外包商**：无独立商业主体、无合同对价，其"报酬"是模型档位配给（五档路由+额度链滑档，17d §2.3）；**不是顾问**：顾问只建议不执行，操作员有执行权（Function Calling 执行循环，17d §2.3）但也无最终决策权（locked 区不可变更，17c §3.1）；**不是纯工具**：拥有 free 区创造决定权与子代理派遣权（R17-8c③，DECISIONS.md:835）——这三点恰好是"员工"与"工具"的分界。
- **"法律和责任身份"在纯软件语境下的落法**（无法人资格，责任=可归因性）：

| 落地物 | 机制 | 事实依据 |
|---|---|---|
| 行为留痕 | op_log.jsonl 每动作一条：`{ts, shot_id, tool, args, result_digest, before/after_snapshot_ref, llm_call_ref}` | 17d §2.5 |
| 责任签名 | handoff_package 含 from_node/to_node/task_status，交接即 crew_bus 事件落档 | 17d §5.3 |
| 人审兜底 | 三层 accountability：判断型岗 owner_signoff / 工具链岗免审 / 高危操作人审闸 | DECISIONS.md:674（RC3） |
| 成本责任 | jobs.py 现金/工时账 + producer 现金账本"每笔调用记引擎/秒数/金额/成败/幂等键" | agents/producer/SKILL.md §2-3 |
| 合法但留痕 | "确定性'行程扩展 pass'认可为护栏批准的确定性补装（**op_log_repair 留痕制度确立**，非纯 LLM 产出但合法）" | DECISIONS.md:858（R17-9-4） |

即：LLM 操作员的"责任身份"= **一条可重放、可归因、append-only 的行为链**（op_log→handoff→cost_ledger），终点由人类签收兜底（RC3+PH2）。

## ④ Skills 是能力还是员工？谁拥有/维护/审批？

**结论：Skills 是能力（程序性知识），不是员工； ownership 归全组共有、维护走纪律、审批走引入审查。**

- **是能力的证据**：培养手册 §1.2 定性——"SKILL.md 是程序性知识的渐进式披露载体——**MCP 给手，Skills 给判断**"（培养手册:76）。skill 没有岗位卡、没有 op_log、没有抽卡配置，不满足 17d §2 操作员六要素中的任何一项主体资格；它是要素②工具箱中"多步封装为单工具"的包装形式之一（17d §2.2）。
- **SKILL.md 四规则**（培养手册 §1.2:78-81）：
  1. 目录结构 `tools/_skills/{skill_name}/SKILL.md`（既有先例 `_skills/k13-version-tree/` 与 `agents/blockout/SKILL.md`）；
  2. 头部 `name + description`（description 决定 Agent 何时加载全文）；
  3. 正文只写**判断与步骤**，不复述工具 schema（schema 在 tool registry）；
  4. 防注入纪律：自研 skills 为主，外部 skills 引入前按 OWASP LLM Top 10 checklist 审查。
- **拥有/维护/审批的三分**：
  - **拥有**：工具注册表（tool registry）是唯一事实源，"认领即授权（A12 工具白名单机制，注册对象改为 registry）"（培养手册 §1.3:97；17d §4）；
  - **维护**：skill 内容随试点踩坑回填——如 N2 `camera-safety` skill 依赖 R17-9-3 运镜防怼脸护栏教训（T1_T2 专项②），即"经验→判断→skill"的培养闭环（培养手册 §1.5）；
  - **审批**：自研 skill 由团队评审采纳（第九轮起"全部走推荐"）；外部 skill 引入须过 R17-8c② 双底线"License 合规且不破坏自包含底线"（DECISIONS.md:835）+ OWASP 审查（培养手册:81）。
- **设计建议**：skill 的职责边界变更（如 vl-selfcheck 口径从"阻塞出片"改为"参考不阻塞"——R17-9-1 已实际发生此类变更，DECISIONS.md:855）应视同权限变更，进任务三①"必须过目清单"第 5 项。

## ⑤ MCP 是通道还是权限边界？

**结论：既是通道也是权限边界——通道在传输层，边界在治理层，两层在同一套双组件上独立演化。**

分层论证：

1. **传输层=通道**：自研 MCP 双组件（Blender addon 内嵌 socket/JSON-RPC + stdio MCP server），是 N2 操作员"伸手"的管道——起步三工具 get_scene_info/render_frame/execute_code（17d §4"进行中"，#40 试点），R17-8a 明文其为"本环节主路径"（DECISIONS.md:833）。五断言全过=通道实证可用（DECISIONS.md:851）。
2. **治理层=权限边界**，四个边界机制：
   - **网络边界**：MCP addon"仅监听 127.0.0.1 + token 校验 + 命令白名单 + execute_code 可配置关闭"（17d §2.3 安全边界；自包含调研 §3 安全基线）；
   - **白名单边界**：A12 工具白名单改写注册对象为 tool registry（17d §6.5），未注册工具不可达——MCP 通道本身不决定能调什么，registry 才决定；
   - **进程边界**：V27/T5 禁区"bpy 不进 Agent 进程"精神保留，MCP addon 使 bpy 在 Blender 进程内执行、Agent 进程仍不 import bpy（17d §6.5"进程隔离"）；
   - **实例边界**：R17-9-5"每 Blender 实例独立端口+PID 文件+输出目录约定，并发作业前必须声明实例归属"（DECISIONS.md:859，源自两代理同端口互杀的协作冲突教训）——这是纯运行时的新边界维度：**同一通道按实例分域**。
3. **为什么"既是通道也是边界"成立而非二选一**：若只有通道无边界，execute_code 类全能工具等于把 Blender 进程整个交给 LLM（越权面=全部 bpy API）；若只有边界无通道，边界退化为静态配置文件无法执行。R17-9-5 的互杀事故正是"有通道、缺实例边界"时的真实故障形态，反证两层缺一不可。
4. **外部引入的 MCP 同理**：R17-8c② 准入双底线（License+自包含）+ 纯云服务走 llm_gateway 式网关留痕（DECISIONS.md:835）——即第三方 MCP 的"边界"前置到引入审批环节。

# 任务二 · LLM↔LLM 冲突处理（七类逐条）

## ① 角色重叠：两个 Agent 以为做同一件事

**防线设计（三层）**：

1. **编制层消重叠——重叠就合并而非协调**：17d §6.3 的合并判例——P3（构建）+P4（动画）合并为 N2 的理由是"MCP 直接操控下'搭建'与'动画'是同一双手的两个动作，拆岗失去意义"（17d §6.3:334）。即编制设计时就以"一双手"为单位划岗，天然减少同对象双操作。
2. **契约层定归属——一个对象/工具/层只有一个 owner**：layer manifest 每层挂 `owner_node`（17d §1.5:113 示例 `"owner_node": "N2_blockout_operator"`）；"一对象只属于一个 layer_id（按其 bpy 类型决定）"（17d §1.4 合并规则:92）；master_v2 19 轨"每轨有 owner 有值"代码化（17d §7.3:397）；工具认领制"在岗位卡 tools[] 中按名认领 registry 中的工具，认领即授权"（培养手册 §1.3:97）——工具被两个操作员同时认领即配置期可检出的重叠信号。
3. **运行层防串台——子代理只纵向汇报**：子代理"结果回传主操作员汇总、通过 crew_bus 事件上报进度"（17d §2.3），无权横向派活给其他操作员；并发作业须先声明实例归属（R17-9-5，DECISIONS.md:859）。
4. **检测**（设计建议）：crew_bus 事件流中若出现"两个 from_node 在同一 aggregate_id（如同一 shot_id+layer_id）上交替写操作事件"，即触发 overlap 告警（dispute 事件类型已有枚举位，三.md:671 六类事件含 dispute/escalate）。

## ② 边界不清：谁决定/执行/审查

**机制：每操作员六要素中的职责边界 + 交接包签名**。

- 六要素本身就是边界定义：任务简报（输入边界：只吃 brief 与上一节点交接包，17d §2.1）、工具箱（能力边界：registry 认领，§2.2）、执行循环（行为边界：白名单工具内迭代，§2.3）、自检（审查边界：只验自己节点的锚点表，§2.4）、留痕回退（责任边界，§2.5）、介入门（升级边界，§2.6）。
- **决定/执行/审查三分写入档位**：locked=老板决定、操作员执行、机器门审查；proposed=操作员提案、老板确认、VL 软门参考；free=操作员决定执行、抽卡评分排序、老板事后挑选（17c §3.1 表：谁定列）。
- **交接包签名**：handoff_package 的 `from_node/to_node/task_status` 三字段即责任交接签名，"下一节点读卡（operator_card）确认输入契约匹配后开工"（17d §5.3:301）——签收动作把"边界不清"转化为"卡不匹配即拒收"的机械判定。
- 打回路由补边界："只在 locked 区违规时打回，free 区永不打回"（17c §4:164；17d §6.5 A21 改写）——防止上游以"审查"为名越界干预下游 free 区。

## ③ 上下文不一致

**机制：A2A handoff_package 与 crew_bus 落档双保险**。

1. **交接包是唯一传递物**：artifacts 只存路径引用不内嵌二进制（17d §5.3:288"路径引用，不内嵌二进制"），`anchor_status` 验收状态随包、`op_log_digest` 摘要内嵌（:291）——下一节点读到的是与上一节点**同一份落盘事实**，不是转述。
2. **crew_bus 保证事件层一致**：先落档后广播（crew_bus.py:15 要素 3"任一回调异常被捕获记录，绝不影响落档"）；idem_key 幂等（:7"同键重复 publish 幂等命中"）；水位表重放"零丢失零重复（R0-O17）跨重启成立"（crew_bus.py:18）——即两个 Agent 无论何时加入，replay 后看到同一事件序列。
3. **消灭双契约漂移**：layer manifest 是"操作员执行后由 export_layer_manifest 自动导出的真实回显，不是又一份要人工维护的契约"（17d §1.5:126）——上下文不一致的经典根源（两份文档各自演化，D9:26 drift 教训，DECISIONS.md:658）在机制上被"执行即回显"消解。
4. **RAG 交接检索**："交接时下一节点拉上一节点 op_log 摘要"（17d §2.7:200）——语义层上下文补充，仍以落盘文件为准。

## ④ 幻觉传播：一个编、另一个当真放大

**机制：交叉复核制度 + "复核 LLM 不赋门职能"的推广**。

1. **事实链溯源断根**：N1 防幻觉护栏——"无 source_span 出处的不进 intent_graph"（T1_T2 专项④ N1 行；17 号草案 §5 source_span 可回溯对策），上游每条约束可回溯到分镜表原文，下游"当真"前可验真。
2. **机器硬门兜底**：G2 元素覆盖 100%、G3b 帧数零误差是机器对账（17c §3.2 保留项）——幻觉即使通过 VL 判读，也会被"LY_GEO 层 objects[] 对账"与帧数对账这类确定性检查拦截（17d §1.6）。
3. **复核 LLM 不赋门职能（核心推广原则）**：R17-9-1 实证裁定——VL 自检 4 轮全否决但根因是场景工艺而非链路缺陷，故"VL 降级为'参考+人审兜底'：VL 判定不阻塞出片，每轮判定+截图全留档，白模动画连 VL 意见一起进人审卡片由导演裁决"（DECISIONS.md:855）。**推广为全队通则（设计建议，依据 R17-9-1 的教训形态）**：任何 LLM 判读输出（VL 意见、评分、另一节点的摘要转述）只能以"证据"身份进人审卡片或评分排序，**永远不能单独成为打回/放行依据**；打回只能由机器门（G2/G3b/schema 校验）或老板触发。这一条恰好切断"幻觉判读→下游当真放大→系统性返工"的传播链。
4. **交接包拒收校验**：下一节点开工前读 operator_card 校验输入契约匹配（17d §5.3:301），schema 不合即拒收——Structured Output 强制 schema 校验使"编出来的格式"进不了下游（17d §9 P0 骨架六件套"交接包/评分卡强制 schema 校验"）。

## ⑤ 冲突仲裁：导演意图 vs 制片约束（设计具体流程）

**现行制度事实**：平级 AI 争执最多 2 轮、第 3 轮强制升级导演岗；方向级分歧老板拍板（三.md:784 5.4 第 3 条）；六类事件含 dispute/escalate（三.md:671）。

**具体流程设计**（设计建议，机制挂靠上述既有制度）：

```
L0 争执登记    任一方 publish crew_bus `dispute` 事件
              payload={shot_id, topic, my_position, other_position, evidence_refs[]}
              ——evidence_refs 强制挂锚点表/manifest/G2 报告等落盘物，
              不接受"我觉得"（对齐三.md:804"数值说话，不评感觉"）
L1 平级协商    ≤2 轮。每轮须以新证据回应（引用对方 evidence_refs 并给出
              反证或修正案），无新证据的重复主张不计轮次直接进 L2
L2 分类路由    第 3 轮强制升级，按冲突类型分流：
              ① 流程/成本类（制片约束侧）→ 契约即规则，机器裁定：
                "无开拍单不花钱；超阈值必熔断"（三.md:772 producer 铁律）、
                quota_gate 账本闸（17d §3 N4 行）——此类不需要人裁
              ② 创意/意图类（导演意图侧）→ 升老板：
                复用人审卡片形态（缩略图/两方案对比/各自主张一句话/
                VL 意见作为参考证据），老板 1 分钟内选择
                （卡片制成本依据：17c §3.3"每镜 ≤1 分钟"）
L3 裁决落档    老板裁决 = 一次 crew_bus `escalate` 事件 + 涉事契约回写
              （先例：R17-9-4"11:1x 卡片裁决"进 DECISIONS.md:858；
              争执全程按 append-only 纪律留档，PK8，DECISIONS.md:401）
```

要点：**制片约束类冲突不浪费老板注意力**（约束本身是老板已签的规则，机器执行即可）；**创意类冲突老板只做选择题不做问答题**（卡片形态，对齐三介入门第 3 门）。

## ⑥ 责任归属：错误定位到哪个 Agent

**机制：op_log 留痕制度支撑归因，五级回溯**。

1. **留痕字段即归因索引**：op_log 每行含 `{ts, shot_id, tool, args, result_digest, before/after_snapshot_ref, llm_call_ref}`（17d §2.5:176）——"施工日志，同时是复现依据"。
2. **分层验收使 FAIL 定位到动作**："验收报告按层分组，FAIL 定位到层=定位到操作动作"（17d §1.6:130）。
3. **责任链签名**：handoff_package 的 from/to/status + crew_bus 事件 aggregate_id 串成链（17d §5.3；jobs_events.py:44 idem_key=`job:<id>:<state>:<updated_ts>`）。
4. **五级回溯路径**（设计建议，全部挂既有字段）：成片缺陷 → 机器门/VL 报告（evidence）→ layer 层（manifest owner_node）→ op_log 行（tool+args+snapshot before/after）→ llm_call_ref（模型档与调用原文）。before/after_snapshot_ref 使任何错误可二分定位到具体动作之间。
5. **混合产出归因**：R17-9-4 先例——确定性补装 pass 单独走 `op_log_repair` 留痕，"非纯 LLM 产出但合法"（DECISIONS.md:858）：即归因不仅区分"哪个 Agent"，还区分"LLM 产出 vs 护栏补装"两类来源。
6. **半硬指标归因模板**：场记旧卡已要求 WARN 必须写明 `ENGINE / BLOCKOUT / BOTH`（script_supervisor/SKILL.md §2-2"不许只报不合格"）——归因到根因类别而非停留在现象，该纪律应随 vl_scorer 转职能继承（设计建议）。

## ⑦ Agent Card 投毒风险：自研轻量 A2A 的对照分析

**A2A v1.0 的风险面**（团队任务书给定前提）：无内置授权机制、宽泛 OAuth 作用域致泄漏/冒充、依赖公网 Agent 发现（`/.well-known/agent.json`）。

**我们的自研落法**（17d §5.2，B17d-4 拍板 DECISIONS.md:844）：operator_card.json（本地 config 文件）+ task 状态机（复用 crew_bus）+ handoff_package（文件落盘）。

| 维度 | 公网 A2A v1.0 的风险 | 我们的暴露面 | 防线 |
|---|---|---|---|
| Agent 发现 | 公网 `/.well-known/agent.json` 可被伪造/劫持，冒充合法 Agent | **不存在**：operator_card 是仓库内 config 文件，无公网发现机制（17d §5.2 路径 `AI影视团队v2/config/operators/`） | 风险面整体消除——"我们不依赖公网 Agent 发现" |
| 授权 | 无内置授权、OAuth scope 过宽 → 越权调用 | 信任域=单机单仓库（crew_bus/jobs/manifest 全在本地，17d §5.1"五节点同机协作，无此需求"）；不需要 OAuth 级授权 | 授权收口为 tool registry 认领制（培养手册 §1.3"认领即授权"）+ A19 权限矩阵（N2 写 manifest、全组读，17d §6.5） |
| 卡片篡改 | 中间人改写能力名片 | 卡片是文件，可被误改/脚本误写 | **设计建议**：operator_card 变更视同权限变更进老板过目清单（任务三①第 5 项）；变更走 doc gate 式纪律（WD4 核心 fail 先例，DECISIONS.md:580） |
| 任务消息投毒 | 恶意 message part 注入指令 | handoff_package 的 brief_for_next 字段是 LLM 可读文本 | path 白名单（artifacts 限项目目录内路径）；schema 校验强制（17d §9） |
| 工具描述投毒 | 第三方 MCP server 描述恶意指令（Tool Poisoning） | **我们最大的真实风险面**：R17-8c② 允许引入第三方 MCP/skills | 培养手册 §1.2 规则 4（外部引入先按 OWASP LLM Top 10 审查）+ T1_T2 装备矩阵 #60（自研 skills 为主、外部先审后用、外部素材入库清洗） |
| 子代理冒充 | 恶意 Agent 伪装子代理上报 | 子代理经 crew_bus 上报（17d §2.3），无签核/花钱工具权限 | sign工具与 quota_gate 不进子代理认领范围（设计建议，依据 A12 认领即授权的收口逻辑） |

**结论**：A2A v1.0 的核心风险（公网发现被冒充、OAuth 作用域泄漏）在我们的架构里**因威胁模型不同而不存在**——单机协作、无跨组织互操作（17d §5.1 判断"完整 A2A 协议栈面向跨组织/跨框架互操作，本项目无此需求"）。我们要防的是它的本地变体：**文件完整性（卡片/契约篡改）、交接内容投毒（brief 注入）、第三方工具描述投毒**——三者分别由过目清单、schema+路径白名单、引入审查承接。

## ② 操作员 free 区自由发挥 vs 契约 locked 硬校验：冲突消解流程

**制度事实**：三档位定义与验收分级（17c §3.1 表：locked=硬门导演签收/proposed=软门转人审/free=不验收）；档位流转与收割（17c §3.1"任何 proposed 项导演可一键升 locked 或降 free；free 区变体可收割升 proposed"）；A21 打回改写（17c §4:164"打回只发生在 locked 区违规…free 区永不打回"）。

**冲突消解流程**（四步，全部挂既有机制）：

```
Step1 检测    分层验收按层核：LY_GEO 验 A1/A2、LY_CAM+LY_PROXY 验 A3、
              LY_ANIM+LY_RENDER 验 A4（17d §1.6）——违规自动定位到层，
              无需人工分辨"这是自由还是越权"
Step2 分档处置
   locked 违规 → 自动打回（G2/G3b 机器门，17c §3.2），带四要素打回单
                （哪帧/什么问题/违反什么/改什么方向，三.md:847-854）
   proposed FAIL → 转人审不自动打回（17c §3.1），老板在卡片上定夺
   free 区产出 → 永不打回（A21 改写，17c §4）；进入抽卡评分
Step3 收割    若 free 区变体被导演选中 → 变体描述写回 prompt_hint 并升
              proposed（17c §3.1"收割不确定性的制度化"）——
              自由与契约的冲突以此正向消解：自由产出新契约
Step4 留痕    档位流转/收割/打回全部落 crew_bus 事件与 op_log
              （append-only，PK8，DECISIONS.md:401）
```

本质（17c §0:12 的哲学落地）：接口决定自由度流向——冲突不是"压制自由"或"放松契约"，而是**把自由放进对的格子**（free 格），格子外自动打回。

## ③ 三介入门之外老板是否真的不介入：介入频率设计

**结论：三介入门之外按"例行全自动 / 例外升级 / 紧急熔断"三频段运行，且总介入量有预算约束。**

| 频段 | 覆盖 | 机制 | 事实依据 |
|---|---|---|---|
| **例行全自动**（零介入） | free 区生产、proposed 提案、本地抽卡 N=3~4、VL 自检闭环、G2/G3b 机器门、schema 校验、交接包流转、op_log 回灌 | 三介入门明文"三处，其余不介入"（17d §2.6）；R17-8b"老板=导演，只在关键门处介入"（DECISIONS.md:834） |
| **例外升级**（事件触发，自动升老板） | ① 争执 3 轮（三.md:784）；② escalation 三条件：locked 重试 2 次 FAIL / 工具连败 ≥3 / 将超预算（培养手册 §1.1，T1_T2 专项④"岗位卡 escalation 三条件"）；③ 人审卡片本身（每镜 top-3，R17-9-4 卡片裁决已实证，DECISIONS.md:858） | 升级通道=crew_bus escalate 事件（三.md:671） |
| **紧急熔断**（停机+签字） | 单镜超限/项目累计超限：per_shot_warn ¥5 / per_shot_stop ¥10 / project ¥100（三.md:918 prices.json circuit_breaker）；"熔断后不自动恢复，必须老板签字解锁"（三.md:896）；流程事故类（如实例互杀）即时裁定成运行规范（R17-9-5，DECISIONS.md:859） |

**介入频率是健康指标**（设计建议）：P2 验收断言已有量化口径——"人审介入总时长 ≤ 全片镜数×1 分钟量级"（17d §8:442）。建议将其推广为常驻指标：若实际介入频次持续超预算（例外交警 > 每日 3 次或熔断 > 每周 1 次），说明escalation 阈值或护栏配置有系统性问题，应回修护栏而非加人审——这与 R17-9-1 的教训同构（VL 误报率高→不是加人审而是修场景工艺，DECISIONS.md:857"先修 VL 再开下游"）。
