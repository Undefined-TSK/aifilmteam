# 数字员工培养与监控手册（2026-10-04）

> 起草：架构师高见远（employee-manual）｜性质：17d《全链路操作员架构（重构版）》的**"培养与运维"配套篇**——17d 回答"操作员架构长什么样"（唯一权威，本文只引用不重复），本手册回答老板两问：**怎么培养一个 LLM 数字员工、怎么设定、怎么跑通全流程、之后随时监控**；以及**已有资产对单个数字员工有什么用、对 LLM 组成的团队有什么用**。
> 纪律：技术名词语义统一引用《A智能体技术全景名词表-2026-10-04.md》（下称"名词表"）；17d 拍板记录 B17d-1~5 见 DECISIONS.md 第十七轮；未验证处如实标注；本文只写自身一个文件。
> 实现宗旨：**尽量用 Python 库实现**——能纯标准库就纯标准库，需要时用成熟 PyPI 库（逐处注明），全篇零新建二进制依赖。

---

## 0. 总纲：数字员工 = "岗位卡 + 五件套 + 台账"三合一

一个数字员工（17d 语境=操作员节点 N1~N5）的培养，拆成三层：

| 层 | 内容 | 载体（全部现成资产或纯文本件） |
|---|---|---|
| **身份层** | 岗位卡 operator_card（17d §5.2，对齐 A2A Agent Card） | `config/operators/{node_id}.card.json`（新建，纯 JSON） |
| **能力层** | 培养五件套：人设简报 / skills / 工具箱 / 知识库 / 记忆 | 岗位卡内嵌 system prompt + `_skills/` 目录 + tool registry（17d §4）+ RAG 四层（17d §2.7）+ op_log.jsonl |
| **运维层** | 事件总线 + 作业账本 + 滑链留痕 + 监控面板 | crew_bus.db + jobs.db + llm_switch_log.jsonl + 本手册 §4 监控方案 |

与 17d 六要素的对应：五件套覆盖要素①简报、②工具箱、③执行循环（由 llm_gateway+tool registry 承担，属"已设定的底座"而非"要培养的内容"）、⑥导演介入门（写进岗位卡升级上报条件）；要素④⑤（VL 自检/留痕回退）是工具箱与记忆的内置行为。**五件套是"养"，六要素是"设"。**

## 1. 单个数字员工的培养五件套

### 1.1 人设与简报：岗位卡 system prompt 模板

岗位卡=操作员的"入职合同"。17d §5.3 的 operator_card.json 是机器可读契约，其 `brief_for_next` 之外还应内嵌一段 **system prompt**。白模操作员岗位卡的**完整可填写模板**如下（新建文件即用，`〈〉` 为填空位）：

```jsonc
// AI影视团队v2/config/operators/N2_blockout_operator.card.json —— 白模操作员岗位卡（模板）
{
  "card_version": 1,
  "node_id": "N2_blockout_operator",          // 对齐 17d §3 五节点编号
  "display_name": "白模搭建操作员",
  "upstream": ["N1_intent_operator"],
  "downstream": ["N3_control_operator"],

  "io_contract": {                              // A2A Agent Card 对应字段
    "accepts": "handoff_package(v1).artifacts.brief_for_next",   // 17d §5.3
    "emits":   ["layer_manifest", "shots/{shot_id}/frames|exr|video", "handoff_package(v1)"]
  },
  "tools": ["blender_mcp.get_scene_info", "blender_mcp.render_frame",

  "subagent_policy": "自检子代理用 vision 档；渲染变体可并行派发，经 crew_bus 上报",

    "identity":  "你是《〈项目名〉》项目的白模搭建操作员。你是一位有手有脚的真实的人：用 blender_mcp 工具在 Blender 里直接搭建、摆机位、打灯、做动画——你不是翻译官，不存在'把意图翻译成固定数值'这回事（R17-8a/R17-8b）。",

      "工具连续失败 ≥3 次（MCP 断连/渲染崩溃）→ 上报并挂起任务，crew_bus 发 job.failed",
```

**简报（task_brief）组装配方**（17d §2.1 的落法）：`导演三档位指令 + 上一节点 handoff_package + RAG top-k（同 SET 历史镜头/同元素类型教训/风格指南段）`，拼装后强制过 Pydantic schema 校验（Structured Output 纪律，名词表 P0）。

### 1.2 skills：SKILL.md 手册怎么写

按名词表 §二 Agent Skills（开放标准 agentskills.io，2025-12 开放）：**SKILL.md 是程序性知识的渐进式披露载体——MCP 给手，Skills 给判断**。写法规则：

1. 目录结构：`tools/_skills/{skill_name}/SKILL.md`（+ 可附脚本/参考件）——既有先例 `_skills/k13-version-tree/` 与 `agents/blockout/SKILL.md` 照此格式沿用；
2. SKILL.md 头部写 `name + description`（name 供渐进式披露索引，description 决定 Agent 何时加载全文，务必一句说清触发场景）；
3. 正文只写**判断与步骤**（何时用哪个工具、参数怎么选、失败怎么救），不复述工具 schema（schema 在 tool registry）；
4. 防注入纪律（名词表 Tool Poisoning 条）：自研 skills 为主，外部 skills 引入前按 OWASP LLM Top 10 checklist 审查。

**白模操作员第一份 skill 目录草案**（P0 试点 #40 配套，建议顺序）：

| skill 目录 | 装什么判断 | 依赖工具 |
|---|---|---|
| `blockout-build/` | 空场→按锚点搭建的顺序心法：先 LY_GEO 后 LY_PROXY→LY_CAM→LY_LIGHT；命名规范 CHAR_/PROP_/SET_（D16）；对象上限三档 | blender_mcp 三起步工具 |
| `vl-selfcheck/` | 渲染截图→判读→修正→复验的闭环步骤；崩坏一票否决的识别口径 | vl_scorer、render_frame |
| `snapshot-rollback/` | 何时主动存快照（每完成一层/每版白模）、回退操作与 op_log rollback 记录纪律 | snapshot_rollback |
| `manifest-export/` | 交付前导出 layer manifest 并自检 11 层归属（bpy 类型→layer_id 映射口诀，引用 17d §1.4 表） | export_layer_manifest |
| `rag-lookup/` | 简报组装前查 rag_kb 的时机与关键词构造法（同 SET/同元素类型/历史 FAIL） | rag_kb |

### 1.3 工具箱：从工具注册表认领工具

认领方法（对齐 17d §4 tool registry）：

1. 在岗位卡 `tools[]` 中**按名认领** registry 中的工具（一个不废弃，R17-8c 三源制①）；认领即授权（A12 工具白名单机制，注册对象改为 registry）；
2. 包装形式三档按 17d §2.2 选：MCP server 工具（交互式/长任务，如 blender_mcp）／直接 Function Calling（纯 Python 函数+JSON schema，llm_gateway tools 实测路径）／skill（多步封装）；
3. 新工具 schema 由 Pydantic 模型派生（T4 机制沿用），登记 registry 三列（工具名/来源/包装形式/状态）后才能进岗位卡；
4. 第三方 MCP/skills 引入走 R17-8c② 双底线：License 合规 + 自包含；纯云服务一律经 llm_gateway 留痕。

白模操作员认领结果示例即 §1.1 模板 `tools[]` 九件；其余节点认领清单直接引用 17d §3 五节点表的"工具清单"列，不复制。

### 1.5 记忆：三类台账怎么变成"经验回顾"

| 台账 | 现状 | 经验化路径（谁来回灌） |
|---|---|---|
| **op_log.jsonl**（每节点每镜一份：ts/shot_id/tool/args/result_digest/before·after_snapshot_ref/llm_call_ref，17d §2.5） | 字段规格已定，随 P0 试点开始落盘 | **每日 top 失败案例回灌**：一个纯标准库小脚本扫当日 op_log，按 `result_digest 含 FAIL/error` 聚类取 top-3，生成"教训行"（动作-结果-教训三段句）追加进该操作员经验层 RAG——次日简报组装自动命中 |
| **场景快照**（snapshots/{shot_id}_v{n:02}.blend，滚动 10 版+里程碑） | MCP addon 规划件 | 快照版本号即"记忆的章节"：回退+复盘时按 manifest version 联动读 v{n} 前后 op_log 段，复盘行写入经验层 |
| **llm_switch_log.jsonl**（滑链留痕，已实盘：tier/from_model/to_model/reason/error_code） | 已在记录（实读见 2026-10-04 http_502 滑档多条） | 周度聚合：每 tier 滑档率 top 模型→反馈给运维调 llm_router.json 优先序；单操作员视角=它的"体能记录"（本地档不行时靠谁兜底），入经验层摘要 |

回灌闭环本质 = 名词表 Agentic Context Engineering 的 Generator-Reflector 思想的简版（仅借鉴三角色分工，不引入框架）：**Generator=操作员干活留台账 → Reflector=每日脚本提炼教训行 → Curator=教训行写回 rag_index.json 经验层**。全程纯标准库可写。

### 1.6 培养流程 checklist：从零培养一个新数字员工

可执行验收断言式（每条可用 `python -c` 或测试脚本断言）：

```
□ 1. 岗位卡落盘：config/operators/{node_id}.card.json 存在，且 json.load 通过
     断言：五段 system_prompt（identity/duties/tier_reading/self_check/escalation）非空
     断言：tier_reading 三键齐全且 locked 段含"硬校验"字样；escalation ≥3 条
□ 2. 模型档位验证：岗位卡 model_tier 在 runtime/llm_router.json tiers 内
     断言：该档 verified 本地模型连通（dashscope_suite / test_llm_gateway.py 通过）
□ 3. 工具认领：岗位卡 tools[] 每一项都在 17d §4 registry（或登记补充行）
     断言：对每个认领工具能取到 JSON schema（Pydantic 派生或手写），null 即 FAIL
□ 4. skill 装载：_skills/{node 至少 1 个 skill}/SKILL.md 存在
     断言：头部含 name+description 两行；description ≤2 句且含触发场景词
□ 5. 知识库连通：rag_index.json 存在且契约层四件（master_v2/shot_spec schema/
     delivery_spec/qc_rubric）均可被 rag_kb 查询命中 ≥1 条
□ 6. 台账就位：op_log 路径可写（touch 断言）；crew_bus 该 node_id 的 job.* 事件
     可发布可读（test_crew_bus.py 通过即证明总线健康）
□ 7. 冷启动试跑：给它一份最小 task_brief 跑通"读简报→调 1 个工具→写 1 行 op_log→
     产出 self_check_report.json"
     断言：四件产物齐备且 schema 校验 PASS
□ 8. 回退演练：制造一次失败（如断开 MCP），验证 escalation 触发 + job.failed 事件
     落 crew_bus.db + 快照可回退
□ 9. 监控挂网：监控面板（§4）上该节点可见、健康度为绿
全绿 = 该数字员工"毕业上岗"。
```

## 3. 全流程跑通视角：五节点接力怎么走

### 3.1 handoff_package 流转图（一场戏）

```
导演（老板）
 │ 三档位指令
 ▼
[N1 意图理解] ── handoff_package#1（intent_graph+brief 素材，导演签收 intent_graph）
 │ crew_bus 事件: handoff.completed(from=N1,to=N2,payload_path=…)
 ▼
[N2 白模搭建] ── 交互式搭建 → 多版白模（本地 N=3~4，0 元）→ VL 自检择优
 │   产物：layer_manifest / frames / exr / video / self_check_report
 │ handoff_package#2（artifacts 路径引用 + op_log_digest + anchor_status）
 ▼
[N3 控制图派生] ── exr→控制图五件套 + prompt_builder（manifest→逐镜 prompt 模板）
 │ handoff_package#3
 ▼
[N4 云端重绘] ── 分层抽卡（B3）：本地候选→VL 三维评分→云端 VACE 只烧胜者
 │   产物：重绘片段 + top-3 人审卡片 → 导演选片（HITL 介入门③）
 │ handoff_package#4（candidate_pool.top3 + 人审结果）
 ▼
[N5 配音配乐剪辑] ── tts/bgm/sfx → whisper 对轴 → mix/cut → qc_media 校验
 │ handoff_package#5（成片 + anchor_status 全 PASS）
 ▼
成片交付（tech_delivery_spec 校验过 → 导演签收）
```

每一跳 handoff 动作=一条 crew_bus 事件；失败交接按 17d §5.3 只在 locked 区违规时打回上一节点。20 字纪律：**路径引用不内嵌二进制、op_log 摘要必带、anchor_status 必填**。

## 4. 监控体系："随时监控"

### 4.1 已有监控资产盘点（五个数据源，全部已存在或规格已定）

| 数据源 | 位置 | 能回答的问题 | 现状 |
|---|---|---|---|
| ① crew_bus 事件流 | runtime/crew_bus*.db（SQLite WAL，events 表） | 每个节点在干什么？handoff 卡在哪一跳？ | 已实现（test_crew_bus 全 PASS） |
| ② jobs 状态 | pipeline/jobs.db + job.* 事件 | 作业成功率/失败原因/现金工时账 | 已实现（jobs_events 已接线） |
| ③ llm_switch_log | runtime/llm_switch_log.jsonl | 模型滑档频率/故障模式（502 等）/哪档不稳 | 实盘运行中 |
| ④ op_log | logs/op_log/{node}_{shot}.jsonl | 每操作员动作数/错误数/回退次数 | 规格已定（17d §2.5），随 P0 落盘 |
| ⑤ 测试断言 | test_*.py / dashscope_suite | 底座是否健康（总线/网关/schema/模型连通） | 已实现，可定时跑 |

另有额度水位：bailian 台账 + budget_manager（VACE ≤18/50 池）。**缺的不是数据，是一个聚合展示面。**

### 4.2 监控面板 MVP 方案（纯 Python 轻量方案，只出方案不实现）

**推荐栈：FastAPI + uvicorn + Jinja2 + sqlite3/json 标准库**——理由：`tools/api_server.py` 已是 FastAPI+uvicorn 且托管 web/，监控页直接挂进去零新进程；Jinja2 服务端渲染一张状态页，前端零打包。备选：若要求零第三方依赖，可用纯标准库 `http.server` + 手拼 HTML（多写约 100 行，功能等价）。

**MVP 功能清单（P1，约 5 个页面区块 + 2 个 API）**：

| # | 区块 | 数据源 | 展示 |
|---|---|---|---|
| 1 | 五节点健康度 | ①+④：按 node_id 聚合最近 30min 的 job.* 与 op_log 行数/错误数 | 绿/黄/红卡（绿=有进展无错误；黄=错误率>10% 或 handoff 停滞>10min；红=job.failed 或工具连败≥3） |
| 2 | 额度水位 | budget_manager 台账 + bailian 台账 + jobs 现金账 | VACE 池余量条（18/50）、各档模型当日调用量、到期倒计时（快到期序见 R17 收敛 6 条） |
| 3 | 卡点告警流 | ①事件流过滤 handoff 停滞/job.failed/escalation 关键词 | 倒序告警列表 + ntfy 推送（K-REV-2 告警主出口，ntfy 纯 HTTP 无 Key，requests/httpx 一行调用） |
| 4 | 滑链仪表 | ③ switch_log 按 tier×(from,to) 聚合 | 24h 滑档率表；连续 502 触发区块 3 告警 |
| 5 | 交接链视图 | ① handoff.* 事件 | 当前一场戏的 §3.1 流转图实时版：哪跳 completed/failed/working |
| API-1 | `/api/status` | 聚合①~④ | JSON 总览（给 web/ 工作台或 AG-UI 简版 SSE 消费） |
| API-2 | `/api/alerts` | 区块 3 | JSON 告警（供 ntfy/轮询） |

**实现要点**：
- 读取层全部纯标准库：sqlite3 读两个 db（WAL 只读连接 `file:...?mode=ro`）、jsonl 逐行 tail、json 读路由表/台账；聚合用 dict/Counter，无需 pandas；
- 告警规则先硬编码三档阈值（上表括号内），P2 再外置 `config/monitor_rules.json`；
- 刷新：Jinja2 页面 meta refresh 15s 或 SSE（AG-UI 简版，名词表 P1 项）——MVP 用 meta refresh 即可；
- 部署：挂进 api_server.py 同进程（新 router），或独立 `tools/monitor_panel.py` 单文件（建议后者，与 api_server 解耦，纯增量）；
- 安全：仅监听 127.0.0.1；不展示 secrets 路径内容；
- 数据保留：面板只读不写，零侵入五个数据源。

### 4.3 监控节奏建议

- 实时：面板常开（老板"随时监控"的主入口）；
- 每日：§1.5 经验回灌脚本跑一次（top 失败案例进 RAG）；
- 每周：test_*.py + dashscope_suite 全量跑（底座体检），滑链周报调路由。
