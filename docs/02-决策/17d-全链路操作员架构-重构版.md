## 0. 总纲：一句话哲学与本文档的角色

**全链路每个环节的 LLM 都是"有手有脚的真实的人"=操作员节点**：通过 Function Calling 伸手调用 Tools（工具本体），工具从 MCP/skills 工具箱取用，忙不过来可派子代理；有渲染回看（眼）、有创作判断（脑），灵活且有创造性地完成工作——**绝不充当翻译官**，不存在"意图预先翻译成固定代码/数值"的环节。老板=导演，只在三档位指令、锚点签收、人审卡片处介入（R17-8b 原文）。

与旧文档（17 号草案）的关系：17 号草案的"五段流水线+四门验收"是在"1:1 复刻"哲学下的结构化翻译方案，R17-8 已裁定该哲学错误（把灵活意图死板翻译成固定数值=在管线最上游杀死创意）。本文档**替代其架构部分**；17c 文档（分层锚点/抽卡分层/可读性三策）作为本文档 §1/§3/§8 的直接上游继续有效。

本文档五个新增核心件：

## 1. 分层白模数据契约（按元素类型分组）——核心枢纽章节

> 本章是"节点间传递"（§5 交接包）与"分层验收"（§3 各节点锚点）的枢纽。先盘点 Blender 可加入 3D 场景的元素类型全集（以 bpy 官方数据模型为准），再盘点 LLM 的操作面，然后按元素类型分层。

### 1.1 为什么必须先盘点元素类型（老板修正的落法）

旧示范（角色层/道具层/场景层）是**业务视角**分层，缺陷：①层的语义随剧本变化（这场戏"猫窝"是主角，下场就是道具），契约不稳定；②与 Blender 原生数据模型（Collections/Objects/DataBlocks）不对齐，操作员每次都要做一次"业务层→bpy 结构"的翻译——**这恰恰又造出一个翻译层**，违背 R17-8a"LLM 直接操控、不留预设翻译"的哲学。

修正后的原则：**层=元素类型（bpy 原生概念），语义单一、契约稳定、LLM 零翻译**。业务身份（这是角色还是道具）不进层的定义，进 layer manifest 的 `description`/`semantic_label` 字段。

### 1.2 元素类型全集盘点（依据 bpy 官方数据模型）

**A. 场景对象层——`bpy.data.objects`，对象类型枚举（Object Type Items）16 种**（出处：docs.blender.org/api/4.4/bpy_types_enum_items/object_type_items.html）：

| bpy 枚举 | 含义 | 白模管线中角色 |
|---|---|---|
| MESH | 网格 | **几何白模主体**（基本体拼装，01-blender D4 灰 0.55） |
| CURVE / SURFACE / META / FONT | 曲线/曲面/融球/文本对象 | 轻量使用（文本做场记板、curve 做轨迹引导线） |
| CURVES / POINTCLOUD / VOLUME / GREASEPENCIL | 新毛发/点云/体积/蜡笔 | 白模不用（free 区） |
| ARMATURE / LATTICE | 骨架/晶格 | 白模不用（角色绑定属写实化阶段） |
| **EMPTY** | 空物体 | **走位代理/父级锚点**（17 号草案 performance 轨的正宗 bpy 承载体） |
| **LIGHT**（POINT/SUN/SPOT/AREA） | 灯光 | 氛围倾向载体（F2 自由区） |
| LIGHT_PROBE | 光照探针 | 白模不用 |
| **CAMERA** | 相机 | 运镜锚（A3） |
| SPEAKER | 扬声器 | N5 阶段可用 |

**B. 对象附属栈**（挂在对象上）：Modifier 栈（bpy.types.Modifier 子类）、Constraint 栈（Track To 跟拍等）、物理属性（Rigid Body/Cloth/粒子系统/力场）、动画数据 AnimData→Action→FCurves（关键帧）。

**C. 独立数据块**（`bpy.data` 容器，对象间共享；出处：salivity.github.io/blender/article/what-is-bpy-data-in-blender-python-scripting）：materials、images、node_groups（**几何节点树/着色器节点树/合成节点树**）、actions、worlds（世界环境）、sounds、fonts、collections（组织容器）、scenes、view_layers。

**D. 场景级**：world 环境设置、Compositor 合成节点树、View Layer、渲染设置（引擎/分辨率/fps/色彩管理 D4）。

### 1.3 LLM 操作面盘点（操作员"能往 3D 空间添加/编辑什么"）

| # | 操作 | bpy 落点 | 白模阶段默认档位 |
|---|---|---|---|
| O1 | 添加/变换对象（基本体/灯/相机/空物体/文本） | bpy.ops.mesh.primitive_*、object.new | locked 项硬校验，free 项自由 |
| O2 | 命名与集合归组 | object.name 规范（CHAR_/PROP_/SET_）、collection.objects.link | 规范 locked（命名规范是契约） |
| O3 | 材质指定 | object.material_slots、material.new | 灰模固定（D4） |
| O4 | 修改器添加 | object.modifiers | free |
| O5 | 关键帧动画 | keyframe_insert（loc/rot/scale/focal） | 轨迹锚 locked/proposed，中间过程 free（D20 插值显式） |
| O6 | 灯光参数 | light.energy/color/type | free（F2） |
| O7 | 相机参数 | camera.lens/dof | move_type 方向 proposed，数值 free（F5） |
| O8 | 约束 | object.constraints（Track To 等） | free |
| O9 | 粒子/物理/力场 | object.rigid_body 等 | **白模禁用**（微动态全让给生成模型，F3） |
| O10 | 几何节点 | node_groups | 白模不用（扩展区） |
| O11 | 世界环境 | world 节点 | free |
| O12 | 场景/渲染设置 | scene.render / view_layer | **locked**（fps/帧数=锚点 A4 派生，分辨率=交付规格） |

### 1.4 层清单：11 个元素类型层 × 4 个视图组折叠

判据（老板原话落地）：**分得细一点、越细越好，但不是越多越好——判据=LLM 理解负担最小、每层语义单一清晰**。落法：**契约层按 11 个元素类型层细记（manifest 层），LLM 视图层按 4 个功能组折叠呈现**——细在契约、少在呈现，两头兼得。

| layer_id | 元素类型（bpy 依据） | 语义（单一） | 视图组 | 白模档位 |
|---|---|---|---|---|
| LY_GEO | MESH（含 CURVE/FONT 轻用） | 几何实体 | G1 几何组 | 布局锚 A1/A2 |
| LY_MAT | materials 槽 | 材质占位 | G1 几何组 | 灰模固定 |
| LY_MOD | modifier 栈 | 形变整形 | G1 几何组 | free |
| LY_PROXY | EMPTY | 代理/父级锚 | G2 运动组 | 轨迹锚 A3/F6 |
| LY_ANIM | AnimData/Action/FCurves | 关键帧 | G2 运动组 | 节拍锚 A4 |
| LY_CAM | CAMERA | 相机 | G2 运动组 | 运镜锚 A3 |
| LY_LIGHT | LIGHT/LIGHT_PROBE | 灯光 | G3 光照组 | free（F2） |
| LY_WORLD | worlds | 环境背景 | G3 光照组 | free |
| LY_PHYS | 物理/粒子/力场 | 模拟 | G4 配置组 | 白模禁用 |
| LY_NODE | node_groups（几何/合成节点） | 程序化 | G4 配置组 | 扩展区 |
| LY_RENDER | scene.render/view_layers | 渲染配置 | G4 配置组 | locked（A4 派生） |

合并规则（层间语义出现混合时）：一对象只属于一个 layer_id（按其 bpy 类型决定）；对象级附属（modifier/anim）随主对象所在层记录明细、但**验收时按附属层单独核**——避免"一个对象拖四个层"的理解负担。

### 1.5 layer manifest 契约（JSON schema 草案）

```jsonc
{
  "manifest_version": 1,
  "set_id": "SET_apartment",            // 场景级 manifest；每镜 delta 另存
  "delta_for_shot": "1-2",
  "view_groups": {                      // LLM 视图组折叠（呈现层）
    "G1_geometry": ["LY_GEO", "LY_MAT", "LY_MOD"],
    "G2_motion":   ["LY_PROXY", "LY_ANIM", "LY_CAM"],
    "G3_light":    ["LY_LIGHT", "LY_WORLD"],
    "G4_config":   ["LY_PHYS", "LY_NODE", "LY_RENDER"]
  },
  "layers": [{
    "layer_id": "LY_GEO",
    "element_type": "MESH",             // bpy Object Type 枚举名（§1.2 表）
    "blender_collection": "COL_SET_apartment_GEO",   // 与 Blender Collections 一一映射
    "objects": ["SET_floor", "SET_wall_N", "PROP_catbed", "PROP_desklamp"],
    "description": "出租屋主场景：窗边藤编猫窝（E-003，locked）、左侧桌上暖光台灯（E-004）",  // B4② 逐对象语义句
    "owner_node": "N2_blockout_operator",
    "anchors": [{                       // 分层锚点：每层只挂自己类型的锚
      "anchor_type": "existence",       // existence/layout/trajectory/duration/none（17c §3.1 anchor 枚举）
      "tier": "locked",                 // locked/proposed/free（B1 三档）
      "spec": "PROP_catbed 靠窗存在；窗帘 MESH 窗侧",
      "verify": "G2 元素覆盖硬门 + VL 拓扑判读",
      "source_span": "分镜表 1-2 description"
    }],
    "metadata": {"prompt_hint": "窗边一个空的藤编猫窝，垫布翻起", "appears_in": ["1-1", "1-2"], "version": 3, "snapshot_ref": "snapshots/1-2_v03.blend"}
  }]
}
```

契约性质：**scene_skeleton.json 的替代者**（差异见 §6 对照表）。生成方式：白模操作员（N2）在搭建过程中由 MCP 工具 `export_layer_manifest` 自动导出（bpy 场景树→manifest，零人工），不自 LLM 手写——manifest 是"操作的真实回显"，不是又一份要人工维护的契约（这是与旧 scene_skeleton 的本质区别：旧契约=先生成后执行，新 manifest=执行后导出）。

### 1.6 分层验收（连接 §3）

- 每层只验自己类型的锚（LY_GEO 验 A1/A2、LY_CAM+LY_PROXY 验 A3、LY_ANIM+LY_RENDER 验 A4）→ 验收报告按层分组，FAIL 定位到层=定位到操作动作；
- G2 元素覆盖门按 LY_GEO 层 objects[] 对账；G3b 帧数门按 LY_RENDER+LY_ANIM 对账；
- 下一节点（N3 控制图派生）按层选取控制信号：LY_GEO→深度条件、LY_PROXY/LY_CAM→轨迹/运镜参考、LY_LIGHT/LY_MAT→prompt_hint 语义词（17c §3.4 策略②的分层扩展）。

### 1.7 调研出处（分层与 scene graph 先例）

- bpy 元素类型官方模型：https://docs.blender.org/api/4.4/bpy_types_enum_items/object_type_items.html ；https://docs.blender.org/api/current/bpy.types.html （B/C/D 类数据块）
- bpy.data 数据库结构：https://salivity.github.io/blender/article/what-is-bpy-data-in-blender-python-scripting
- Collections 工业级分层管理（集合=数据容器非文件夹、命名规范 [类型]_[功能]_[版本]、视图层驱动渲染）：https://tsight.io/articles/19689907 ；https://www.2ds.cn/?p=27311 （嵌套集合+View Layer 三流派评测）；http://www.hqwc.cn/news/1457612.html （分层渲染与合成）

## 2. 操作员节点标准（六要素）

> 每个操作员节点=一个 LLM Agent 实例 + 工具箱 + 自检闭环。六要素为标准配置，缺一不成节点。

### 2.1 要素① 任务简报输入

- **格式**：`task_brief.json`——intent_graph 降级后的形态（R17-8a："intent_graph 契约降级为给白模代理的任务简报，不再是代码生成规格"）。
- **内容**：①本节点使命一句话；②tier 三档约束项清单（locked/proposed/free，B1 字段：tier+anchor+prompt_hint+source_span，见 17c §3.1）——locked=硬校验、proposed=软门+VL 参考、free=不验收只进抽卡评分；③输入产物引用（上一节点 handoff 包路径，§5）；④本节点锚点表（验收判据）；⑤抽卡配置（N 值/预算）。
- **组装**：由导演指令（三档位）+ 上一节点交接包 + RAG 检索（§2.7）拼装。**不再有"结构化意图图→逐字段执行"的翻译语义**——brief 是给"人"的工单，不是给编译器的规格。
- 与 intent_graph 的关系：intent_graph 的 schema 保留（含 B1 三字段，已裁定生效），但其消费语义从"对账规格"降为"brief 的素材库之一"。

### 2.2 要素② 工具箱（来源与包装形式）

- 三源制（R17-8c）：①自研代码全部降维为工具（一个不废弃，§7 盘点）；②第三方开源 MCP/skills 可引入（License 合规+自包含底线：可随项目分发的优先，纯云服务走 llm_gateway 式网关留痕）；③可派子代理。
- 包装形式三档：**MCP server 工具**（自研 stdio MCP server，走 Blender addon 等）、**直接 Function Calling**（纯 Python 函数+JSON schema，llm_gateway tools 实测路径，qwen3:8b 三连测全绿）、**skill**（多步封装为单工具，如 cloud_repaint）。
- 工具注册：进 tool registry（§4），schema 由 Pydantic/JSON schema 派生（T4 派生机制沿用）。

### 2.3 要素③ Function Calling 执行循环

- 循环：`读简报 → 计划 → 逐工具调用（Function Calling）→ 观察结果 → 迭代` 直到自检通过或触发升级。
- LLM 底座：tools/llm_gateway.py（已实现，五档路由+额度链滑档，runtime/llm_router.json）；本地 qwen3:8b tools 调用 2026-10-03 三连测全绿（llm_router.json verified 字段）。
- 安全边界：工具白名单（A12 机制沿用）、MCP addon 仅监听 127.0.0.1+token 校验+命令白名单+execute_code 可配置关闭（自包含调研 §3 安全基线）。
- 子代理：操作员可派子代理执行独立子任务（如"渲染 4 个候选变体"并行化），子代理结果回传主操作员汇总——子代理通过 crew_bus 事件上报进度（R8-C-1 契约）。

### 2.4 要素④ 视觉/结果回看自检（VL 闭环）

- 闭环：`渲染截图/帧 → qwen3-vl-flash 判读（vision 档）→ 与锚点表对照 → 不合则修正 → 再看`，替代确定性验收（R17-8a 配套③）。
- 抽卡评分器（G4 转职能，B2）：三维评分 意图符合度 0.45 / 动感 0.30 / 美感 0.15 + 崩坏一票否决（R17-8c 沿用 17c §3.3 权重表）；评分只进抽卡排序，不自动打回——只有 locked 区违规才打回（A21 打回路由改写）。
- 自检产物：`self_check_report.json`（逐锚点 PASS/FAIL + VL 原始输出留痕，无回显按未验处理纪律沿用）。

### 2.5 要素⑤ 全程留痕+快照回退

- **op_log.jsonl**（每节点一份）：每行一条动作 `{ts, shot_id, tool, args, result_digest, before_snapshot_ref, after_snapshot_ref, llm_call_ref}`——操作员的"施工日志"，同时是 RAG 检索语料与复现依据。
- **场景快照**：MCP addon 在关键动作前后自动保存增量 .blend 快照（snapshots/，命名 `{shot_id}_v{n:02}.blend`，滚动保留最近 N=10 版+里程碑版）+ manifest version 递增联动。
- **回退操作**：导演或操作员可指定"回退到第 v3 版快照"→ addon 载入对应 .blend + manifest 回滚 + op_log 追加 rollback 记录（不删历史，只追加）。
- bpy 批渲染主干（R17-8a 配套②）：360 帧正式渲染与 MCP 故障回退走 blockout_batch_render.py 路径，同样记 op_log。

### 2.6 要素⑥ 导演介入门

三处，其余不介入（R17-8b）：
1. **三档位指令**：导演以 locked/proposed/free 标注任务简报（intent_graph 签收是既有动作，B1 已裁定）；
2. **锚点签收**：camera/light 轨等"签数值"改"签锚点"（B2）——白模操作员出锚点草案（锚点表+白模关键帧截图），DP/导演签锚点，master_v2 signoff 机制不变；

## 5. A2A 节点间交接协议（轻量落地）

### 5.1 调研结论（A2A 协议现状）

- Google 2025-04 发布 **Agent2Agent（A2A）开放协议**，50+ 伙伴共建；定位与 MCP 互补（MCP=agent↔tools，A2A=agent↔agent）；构建于 HTTP/SSE/JSON-RPC 2.0 之上；核心概念：**Agent Card**（JSON 能力名片，`/.well-known/agent.json`）、**Task**（生命周期状态机：submitted/working/completed/failed）、**Artifact**（任务产物）、**Message Parts**（多模态内容分片，类型协商）（出处：https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/ ；https://a2acn.com/en ；ADK+A2A 实战：https://developers.googleblog.com/build-cross-language-multi-agent-team-with-google-agent-development-kit-and-a2a/ ）。
- **判断**：完整 A2A 协议栈面向跨组织/跨框架互操作（HTTP 服务化+发现机制），本项目五节点同机协作，无此需求；但其三概念（能力名片/任务状态机/产物封装）与我们的 crew_bus jobs 台账天然同构。

### 5.2 轻量落地设计（不引入完整协议，借鉴三概念）

| A2A 概念 | 本项目落地 | 载体 |
|---|---|---|
| Agent Card | **operator_card.json**：每节点一张（节点名/输入契约/输出契约/工具清单/锚点表/抽卡配置/模型档）——即 §3 表的机器可读版 | AI影视团队v2/config/operators/{node_id}.card.json（新建） |
| Task 状态机 | 任务状态沿用既有 crew_bus/jobs 台账（R8-C-1 事件五要素），不自建 | tools/crew_bus.py + tools/jobs.py |
| Artifact | **handoff_package（交接包）**：上一节点输出=下一节点输入的标准封装 | 文件落盘，路径经 crew_bus 事件传递 |

### 5.3 交接包规格（handoff_package）

```jsonc
{
  "handoff_version": 1,
  "from_node": "N2_blockout_operator",
  "to_node": "N3_control_operator",
  "shot_id": "1-2",
  "task_status": "completed",          // 借 A2A task 状态机：submitted/working/completed/failed
  "artifacts": {
    "layer_manifest": "projects/r4_l1/00_brief/intent/layer_manifest_1-2.json",  // §1.5，分层白模
    "rendered_outputs": ["shots/1-2/frames/", "shots/1-2/exr/", "shots/1-2/video/"],  // 路径引用，不内嵌二进制
    "brief_for_next": {...}            // 给下一节点的任务简报素材（tier 三档已流转）
  },
  "op_log_digest": {"path": "logs/op_log/N2_1-2.jsonl", "n_actions": 47, "errors": 1, "lessons": "窗帘 MESH 遮挡相机轨迹，已挪至 LY_GEO v5"},   // op_log 摘要（RAG 亦检索此件）
  "anchor_status": [                    // 验收锚点状态表
    {"gate": "G2", "result": "PASS", "evidence": "..."},
    {"gate": "G3b", "result": "PASS", "evidence": "..."},
    {"gate": "motion_semantic", "result": "SOFT_PASS", "vl_raw": "..."}
  ],
  "candidate_pool": {"top3": [...], "harvested_variants": [...]}   // 抽卡候选池索引（N4 交接）
}
```

- 交接动作本身是一条 crew_bus 事件（from/to/payload_path/anchor_status）——下一节点读卡（operator_card）确认输入契约匹配后开工；
- 失败交接（task_status=failed）按 A21 改写后路由回上一节点（只在 locked 区违规时打回）；
- 未来商业化升级路径：operator_card 与 handoff_package 字段设计已对齐 A2A 语义，届时加一层 HTTP/JSON-RPC 绑定即可对外暴露，无需重构（借鉴即为此留的接口）。
