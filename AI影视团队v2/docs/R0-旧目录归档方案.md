## 2. 三个方案（按推荐度排序）

### 🥇 方案 A（推荐）：归档真身 + 原位置留"接合点"

```
D:\_ai_film_legacy_2026\           ← 临时文件夹（新建）
├── ai_film_projects\              ← 真身移到这里（同盘 mv，秒级，内容一字不动）
├── AI影视团队\                     ← 真身移到这里
└── _ARCHIVE_README.md             ← 写清"为什么在这、怎么恢复、谁可以删"

原位置：
D:\ai_film_projects\   →  目录接合点（junction）指向归档真身
D:\AI影视团队\          →  目录接合点（junction）指向归档真身
```

| 项 | 做法 | 命令（执行时用，本轮未执行） |
|---|---|---|
| 建临时文件夹 | 新建 `D:\_ai_film_legacy_2026\` | `mkdir` |
| 移动真身 | 同盘移动，**秒级完成、可逆** | `mv /d/ai_film_projects /d/_ai_film_legacy_2026/` |
| 建接合点 | 让旧路径继续可用 | `cmd /c mklink /J "D:\ai_film_projects" "D:\_ai_film_legacy_2026\ai_film_projects"` |
| 写说明 | 归档文件夹内留 README | — |
| venv | 失效则重建（成本低） | — |

**优点**：① 物理隔离达成（"放进临时文件夹"）② 旧路径全部继续可用（`start_server.bat`、git、`api_server.py` 的相对引用、任何外部工具写死的 `D:\ai_film_projects\...` 都能跑）③ 秒级、零复制、零删除、完全可逆。
**缺点**：接合点对极少数工具不透明（git 在 junction 上一般正常；如遇异常回退方案 B）。

### 🥈 方案 B：纯移动（最直白）

直接 `mv` 两个目录进临时文件夹，**不建接合点**。

**优点**：最干净，新旧彻底分离。
**缺点（已升级为"不可行"）**：旧路径全断，而且**不只是配置断——是 195 处字面量路径全断**（见 §1 表）。旧项目里 `tools\jobs.py`、`pipeline\audio_mix.py`、`tools\qc_media.py`、`tools\dit_ingest.py`、`tools\vram_lock.py`、`tools\gen_*.py`、`tests\*.py` 全部用 `r"D:\ai_film_projects"` 这种写法，**一个都不带 `__file__` 动态推导**。加上 `roles\*\*.env` 的 `PROJECT_ROOT` 等配置，移动后**旧项目彻底跑不起来，也无法按原样复现任何历史结果**。
**结论**：**除非老板明确说"旧项目以后只在归档处翻阅、永不运行"，否则不建议采用。**

### 🥉 方案 C：纯复制（最保守）

`robocopy /E` 复制 74 GB 进临时文件夹，旧目录**原地原样保留**。

**优点**：绝对零风险，两边都在。
**缺点**：① 占 74 GB ② 出现"两份真身"，日后**必然**出现"改了哪一份"的混乱（违反老板"新项目只保留一份定稿"的硬约束精神）③ 耗时长。
**适用**：老板要求"必须有一个物理副本作为冷备份"。若要，建议**只复制项目自有的 600 MB**（排除 comfyui/musetalk/models/blender），把 74 GB 的第三方留给原地。

## 5.3 ⭐ 执行中推翻的一个错误判断（重要）

**现象**：`mv /d/ai_film_projects ...` 报 `Device or resource busy`。
**我的错误推断**：以为有进程占用（某进程 CWD 或工作区句柄），并已排查进程可执行路径、全部进程命令行、CWD 候选（cmd / VS Code / Everything / editor_sdk / hermes gateway），差点按老板授权去杀进程。
**真相**：用 **Windows 原生 `Rename-Item` 一次成功** → 这是 **Git Bash / MSYS 的 `mv` 对目录的限制**，**操作系统层面根本没有锁**。

**因此写入本项目规范（永久生效）**：
> **目录/文件操作遇到 unix 工具报「占用 / busy」，先用原生 API（`Rename-Item` / `Move-Item`）复验，确认是真锁再考虑动进程。不要基于 unix 工具的错误码去杀进程。**
