## 1. ⭐ `mpdecimate` 本机实测（ffmpeg 8.1.2）—— 结论推翻了我自己写进 `qc_rubric` 的用法

### 1.1 官方参数（实测回显）

```
$ ffmpeg -h filter=mpdecimate
Filter mpdecimate
  Remove near-duplicate frames.
mpdecimate AVOptions:
   max   <int>    set the maximum number of consecutive dropped frames (positive),
                  or the minimum interval between dropped frames (negative)   (默认 0)
   keep  <int>    set the number of similar consecutive frames to be kept before
                  starting to drop similar frames                              (默认 0)
   hi    <int>    set high dropping threshold                                  (默认 768)
   lo    <int>    set low dropping threshold                                   (默认 320)
   frac  <float>  set fraction dropping threshold   (范围 0–1)                 (默认 0.33)
```

### 1.2 实测：拿**我们自己已跑通的白模粗片**跑一遍

```
输入：blender/shots/_pilot_blockout/blockout_min.mp4   （960×540 / 24fps / 48 帧 / 2.000s）
命令：ffmpeg -i blockout_min.mp4 -vf "mpdecimate=hi=64*12:lo=64*5:frac=0.33" -vsync vfr -f null -
      （注：hi=64*12=768、lo=64*5=320、frac=0.33 —— 正是默认值）
结果：输出只剩 20 帧
     frame= 20 （原 48 帧 → 丢掉 28 帧 = 58%）
```

### 1.3 ⚠️ 结论：**`mpdecimate` 不能当"judder / 错帧"的质量门**

**为什么**：白模粗片是**缓慢 dolly 运镜**，相邻帧本来就高度相似 → `mpdecimate` 把**正常帧误判成重复帧**，一口气丢掉 58%。
**这直接更正了我自己写进 `spec/qc_rubric.json` 的 soft_4_lighting / 硬指标① 里的用法**（原文写着用 `mpdecimate` 统计错帧）。

**正确分工**：
| 用途 | 该用什么 |
|---|---|
| **真实重复帧压缩**（如源素材本来就有静止段、要降码率） | ✅ `mpdecimate` 可用（但要接受它对慢速运镜的激进判定） |
| **judder / 帧率漂移 / 错帧检测（质量门）** | ❌ **绝不能用 mpdecimate** |
| ↳ 应改为 | **时间戳间隔一致性检查**：`ffprobe -show_frames` 看 `pkt_dts_time` / `best_effort_timestamp_time` 的**间隔分布是否均匀**；同时比 `r_frame_rate` 与 `avg_frame_rate` 是否一致 |

**已知的正确做法（本轮先落地，等调研员补权威出处后再细化）**：
```bash
# 1) 帧率一致性：r_frame_rate（标称）与 avg_frame_rate（实际均值）必须一致
ffprobe -v error -select_streams v:0 -show_entries stream=r_frame_rate,avg_frame_rate,nb_frames -of default=noprint_wrappers=1 in.mp4

# 2) 时间戳间隔分布：导出每帧时间戳，检查相邻间隔是否恒为 1/fps
ffprobe -v error -select_streams v:0 -show_entries frame=best_effort_timestamp_time -of csv=p=0 in.mp4
```
（旧项目 tech_v5 的 QC 正是靠 `r_frame_rate=23.975 != 24.0` 抓出帧率问题的——**说明"比对标称帧率与实际帧率"这条路是有效的**；它比 `mpdecimate` 可靠得多。）

### 1.4 这条实测的连带影响

| 影响对象 | 要改什么 | 何时改 |
|---|---|---|
| `spec/qc_rubric.json` | 把"错帧检测用 `mpdecimate`"改成"用时间戳间隔 + `r_frame_rate` vs `avg_frame_rate` 比对"；`mpdecimate` 仅保留为"重复帧压缩"用途 | **R3**（不跳步，本轮只记录） |
| `agents/script_supervisor/SKILL.md` | 同上，把工具栏里的 mpdecimate 说明改掉 | **R3** |

## 6.2 ⭐ 真正的决策变量不是"省不省拼接"，而是 **17 帧下限**

`num_frames` 最小 **17 帧 = 0.708s @24fps**，所以：

| 镜头类型 | 处理方式 | 分辨率代价 |
|---|---|---|
| 常规镜（≥ 0.71s） | 拆多条、per-shot 生成 | ✅ **可保 720p**（走已验证路径） |
| **亚秒快切（< 0.71s）** | **无法单独成 clip** → 被迫并入单 clip 跨切点 | 总时长 > 6s 时**只能 480p** |

→ **拆镜不是二选一，是混合策略**：应按「**是否存在亚秒切点**」分段排镜，而不是全片统一。
→ 参考片 "10s / 12 shots" 平均 **0.83s/shot**，**正卡在这个临界点上**。
→ **对我们的连带影响**：我们的镜头语法规则写着"ASL 2–5 秒"——这条与"亚秒快切需特殊处理"要一起写进 R3 的镜头规格规范。

# 7. 【勘误第 4 版】帧数公式更正 + 由此产生的**镜头时长量化**后果（影响分镜表模板）

> 来源：`comp-commercial` 的主动勘误（它被 `research-engine-blender` 核出一处口径混淆后复核确认）。**两个成员仍在私下互查——路由问题我会继续收紧，但这次的产出是对的、有价值。**

## 7.1 🔴 更正：`4n+1` 与 `8k+1` 是两个不同后端的约束，**不可混用**

| 约束 | 属于谁 | 起因 |
|---|---|---|
| **`4n+1`** | **WAN**（本地 Wan2.1 / 2.2） | 时序压缩 **4×** |
| **`8k+1`** | **LTX / fal 3DREAL**（云端主力） | 时序压缩 **8×** |

**`45 / 49 / 57 / 65 / 73` 只对 WAN 合法，喂给 LTX 会直接 422。**

**兼容双后端的安全解（建议写进规划表）**：

| 场景 | 允许帧数 |
|---|---|
| 只用 WAN（本地） | `4n+1`：5, 9, 13, 17, 21, 25, 29, 33, 37, 41, 45, … |
| 只用 LTX/fal（云端） | `8k+1`：9, 17, 25, 33, 41, 49, 57, 65, 73, 81, 89, 97, … |
| **两条后端都要兼容** | ⭐ **统一用 `8k+1`** |

**为什么取严者就安全（数学依据）**：`8k+1 = 4(2k)+1` → **`8k+1` 是 `4n+1` 的真子集**，所有合法 LTX 帧数天然满足 WAN 约束（反之不成立）→ **不需要维护两套分镜**。
**旁证**：`121 = 8×15+1 = 4×30+1` **同时合法** —— 这解释了为什么 fal 端点默认值、Mickmumpitz 免费版单次上限**都恰好是 121 帧**（**行业事实标准值**）。

## 7.2 ⭐⭐ 由此产生一条比公式更重要的结论：**镜头时长被量化成离散值**

24fps 下，合法帧数 → **合法时长只有这些点**：

| 帧数 | 时长 | 帧数 | 时长 |
|---|---|---|---|
| 9 | **0.375s** | 65 | 2.708s |
| **17** | **0.708s**（最小可用） | 73 | 3.042s |
| 25 | 1.042s | 81 | 3.375s |
| 33 | 1.375s | 89 | 3.708s |
| 41 | 1.708s | 97 | 4.042s |
| 49 | 2.042s | **121** | **5.042s** |
| 57 | 2.375s | 361 | 15.042s |

**后果（三条，都影响排期与报价）**：
1. **分镜表写"0.5 秒快切"是不可执行的** —— 只能落 **0.375s** 或 **0.708s**。
2. **对外不能承诺连续秒数** —— 客户说"来个 2.5 秒镜头"，技术上**不存在**，只能落 2.375s 或 2.708s。
3. ⭐ **建议**：分镜表模板的时长字段直接做成 **`8k+1` 帧数的下拉枚举**，而非自由填秒数 —— 顺带消除"客户改时长 → 成本重算"的报价抖动。

## 7.4 ✅ 一处"单位不明"—— **主理人用一手原文解掉了**

`comp-commercial` 主动标注：fal 的 `$0.0024075/MP` **计价单位不明**（"每帧·每MP" vs "每秒·每MP" 差 24 倍），故**暂不写进成本对比表**。
**但官方端点页给过完整算例（一手原文，我此前已核）**：

> "Your request will cost **$0.0024075 per megapixel of generated video data (width × height × frames)**, rounded up. For example, if you generate a video that is **121 frames long at 1280 × 720**, your total generated video is **≈112 MP**, and your request will cost **$0.270**."

**验算**：`1280 × 720 × 121 = 111,513,600 ≈ 112 MP` → `112 × 0.0024075 = $0.2696 ≈ $0.270` ✅ **完全吻合**。
→ **单位确认 = 按「总像素数（宽×高×**总帧数**）」计价**，即"每帧·每 MP"那一解释。`$0.0024075/MP` **可以进成本对比表**（≈ $0.27 / 121 帧 @720p）。
→ 已把该证据回给 `comp-commercial`，请它更新成本对比表。
