你要求至少否决 5-8 条。我给 **11 条**，分两档。全收的话否决率 11/95 ≈ 12%，正好落在健康区间（10-20%）——决策记录终于有了"否决"这个信号，说明裁决是真的做过选择题，不是来者不拒。

## 三、MVP 提速：两刀

### 1. 把飞书踢出 MVP（强烈推荐）

MVP 范围表写着"飞书｜移动端必需，只做状态推送+快速审批"。但 MVP 是 **1 角色 + 1 镜头 + 1 工具**、你一个人坐在电脑前手动驱动的流水线——

- 状态推送推给谁？推送给你正在看着的屏幕？
- 移动端审批服务谁？服务不在电脑前的你？你就在电脑前。

飞书机器人哪怕只做推送+卡片，也是独立工程量：机器人注册、卡片搭建、回调接口、网页端状态同步。这些工程量不验证任何 MVP 假设。MVP 自己写得很清楚——"验证的是一条流水线能否跑通，不是权限体系是否完备"，通知体系同理。

建议：MVP 用浏览器通知替代；飞书适配挪到"MVP 验证通过后再加"清单**第一位**。砍掉它，MVP 能快一周以上。

### 2. ComfyUI 部署是关键路径第一块砖

torch wheel 已经下载好（RTX 5070 12GB），装 ComfyUI + 验证 MCP 连通应该是**本周动作**。它不完成，MVP 的"生成工具 1 个（ComfyUI）"就是空中楼阁，网页端做得再漂亮也没东西可渲染。开发顺序建议：ComfyUI 部署第一，网页端骨架（React Flow）并行。

## 四、可以带病定稿的（不要在这轮再改了）

以下问题真实存在，但都是**规格级**不是**架构级**。MVP 开发第一周用一页纸就能定，不值得为它们再拖一轮评审：

1. **未锁定节点被下游引用的默认行为**——建议方向"渲染即快照、引用即版本指针"，实现时定细节
2. **"永远不自动更新下游"对微调太刚性**——影响等级分类（微调自动更新/修改手动确认/重构阻塞），实现时定阈值
3. **意图驱动/预测性预审的位置**——按"设计阶段辅助"实现即可，顺手加一条预审随机扰动防回音室
4. **预算预警线 80% → 70%**——一行字的事，随时可改

判断标准很简单：**改不动架构结论的问题，都不阻塞定稿。** 以上四条怎么改，架构都不变。
